# SCANN v2 ViT 全图检测模型训练指南

## 1. 背景与核心优势
当前项目从传统的 Patch 分类方案（v1）全面升级到了基于 Vision Transformer (ViT) 的全图密集检测方案（v2）。

**这相比于直接套用通用的全图检测有何优势？**
常规的“开箱即用”全图检测模型无法忍受天文图像庞大分辨率下的显存消耗，并且会在多次下采样中“吃掉”极小极暗弱的光点目标。
为了解决这些天文难题，SCANN v2 的设计做了深度特化：
- **重叠切片推理（Tiled Inference）：** 有效规避显存 OOM。
- **Heatmap 回归：** 精准预测点状小天体的中心置信度（配合 Dense Head）。
- **Focal Loss 与数据增强：** 利用天光背景重归一化以及应对极端正负样本不平衡的损失计算。
- **自注意力机制（Self-Attention）：** ViT 利用全局感受野（Global Context），能参考画面远端的星芒、散粒噪点分布去判断局部的可疑点，这种空间参照是传统 CNN 滑窗（甚至由于盲人摸象的缺陷）所做不到的。

## 2. 数据集评估与适用性分析
项目当前拥有的数据集情况：**约 2900 张天文图像，每张包含了数十至数千个密集的标注点**。标注系统包含 8 种详细分类（3 真类，5 假类/伪影）。
**结论：这批数据量绝对足够甚至非常优质。**

主要原因：
1. **百万级的密集像素监督：** 由于标注数量极其稠密，这 2900 张图实质上提供了约 100~300 万实例级别的有效梯度反馈。
2. **丰富的负样本库：** 数据集本身自带大量明确的假阳性目标（卫星轨迹、噪点、衍射芒、结霜）。将它们放入包含整体背景的同一上下文中训练，能完美发挥自注意力机制的学习能力，让模型自动学会把不同形态的噪声剔除。
3. **Focal Loss 专有战场：** 利用如此多的假阳性样本，Focal Loss 能轻松将简单背景降权，将几乎所有的迭代都引导到“困难的暗弱真天体发现”上。

## 3. 面临的风险与数据偏见陷阱
然而，因为实例被强绑定在仅仅 2900 种天区构图背景里（容易造成 **空间与环境相关性偏差 Spatial Correlation Bias**），存在以下需要规避的问题：
- **记忆观测设备特征：** 容易对某一架天文望远镜在某个夜晚特定的畸变、暗角或者读出噪声“过拟合”。
- **同图拥挤假象：** 如果假阳性成群出现，注意力机制可能会将天体的“稀疏/聚集程度”作为它的重要分类判断标准。

## 4. 训练策略与微调建议

### 4.1 数据集划分 (Split Strategy)
**绝对禁止随机打乱图像（Random Split）！**
同一序列或连拍的星图由于地球自转或移动导致的重合率极高。验证集必须完全基于**不同拍摄日期、不同观测设备或者不同天区 (FOV)** 的图去切分，以保证评估的是模型对新环境的真实泛化能力。

### 4.2 极端的天外数据增强 (Data Augmentations)
基于仅拥有的 2900 种物理背景，要求必须采取最为激进的数据增强：
- **几何扩充：** 支持 0、90、180、270 度旋转及横纵镜像翻转（对于天区背景这是完全符合物理法则的）。
- **打碎图像相关性：** 引入类似 Mosaic（四图拼接、重组）或大尺度的破坏性裁剪（Random Crop），强制模型阻断对特定照片边缘光学底噪的记忆。
- **亮度与微弱掩模模拟：** 引入多次高斯模糊模仿不同夜空下的大气视宁度（Seeing）变化，添加高斯与泊松噪声模拟仪器的底噪。

### 4.3 预训练与权重冻结 (Layer Freezing)
采用预训练的通用 ViT 权重文件作为 Base，并在微调前几个 Epoch 采用：
**冻结浅层策略（冻结 Patch Embed 和前几个 Encoder Block）**
原因在于浅层参数已经学会了绝佳的边界与对比度特征提取，强行用有限星空背景重写这些底层参数容易导致网络崩溃。学习率应主要作用于模型深层的自注意力交互（Transformer）与末端的针对点状目标的 `Heatmap` / `BBox 头` 上。

## 5. 进阶训练细节
除常规数据增强和冻结策略外，针对天文图像检测任务还需注意：
- **学习率调度 (Learning Rate Scheduling)：** 建议使用带 Warmup 的余弦退火（Cosine Annealing）。Transformer 结构对学习率非常敏感，Warmup 有助于在初期稳定梯度，避免由于大量的纯背景（极度不平衡）导致模型直接坍缩到局部最优。
- **重叠切片策略的一致性：** 训练时的切片（Tile）大小必须与推理时保持绝对一致，以避免位置编码（Positional Encoding）在推理时因插值产生精度损失。
- **正负样本的定义边界：** 在生成检测 Head 的 Ground Truth（如二维高斯 Heatmap）时，需根据天体的实际像素半径（可以通过 PSF 拟合）动态调整高斯核的半径，而不是使用固定大小，这对大小不一的星系斑块或衍射芒尤其重要。

## 6. 大模型底模与量化策略 (模型压缩)
使用参数更多的底模（如 ViT-Large/Huge）并在训练后进行量化是**非常推荐**的路线。
- **特征解耦：** 大参数量模型拥有更强的特征表达和复杂的注意力机制，能更好地对低信噪比边缘的暗弱星体和复杂的背景光害进行解耦。
- **后置量化防 OOM：** 训练完成后，使用量化感知训练 (QAT) 或训练后量化 (PTQ) 将模型转化为 FP16 或 INT8 进行推理加速，可以有效缓解显存不足和算力瓶颈。
- **注意事项：** 目标检测（尤其是 Heatmap 回归）对激活值的精度要求极高。建议优先使用 **QAT（量化感知训练）**，让模型在训练末期适应低精度分布。直接使用 PTQ 容易导致暗弱恒星的 Heatmap 峰值被抹平变模糊，造成漏检。

## 7. 神经网络各环节流转机制
在端到端的 ViT 全图密集检测方案中，各层运转流水线如下：
1. **预处理与切片 (Preprocessing & Tiling)：** 此环节在数据加载阶段完成。通过 Z-Scale 或 Asinh 非线性拉伸高频 HDR 天文数据，将极暗信号推至神经网络易于处理的工作区间（0-1）。然后将巨幅星图裁剪为定长带重叠区的切片（如 512x512）。
2. **Patch 嵌入层 (Patch Embedding)：** 低级特征提取器。将切片切分为一个个“图元”（如 16x16 像素），并识别最基础的光学特征：如点光源的高斯轮廓（PSF）、十字衍射芒的边缘、散粒噪点的斑纹等。
3. **编解码与自注意力层 (Transformer Encoder)：** 网络主干。浅层建立相邻 Patch 原图联结，深层产生“全局视野”（长距离依赖）。它利用注意机制寻找环境上下文，例如结合局部的亮点和全局的背景底噪/干扰星芒水平，逻辑判断局部异常是真实暗弱天体还是光学底噪假象。
4. **特征金字塔与分类器/检测头 (Neck & Dense Head)：** 网络的输出端。利用特征图逐像素输出 Heatmap（表明该像素为某类别天体中心的概率），同时激活回归器预测目标的亚像素偏移或天体宽高。
5. **后处理层 (Post-processing)：** 通过 NMS（非极大值抑制）去除多余的检测框，最后将所有切片的检测结果拼接融合，去重映射回超大分辨率的原始坐标系内。

## 8. ViT-Huge 显存预估与降存方案
训练 ViT-Huge（约 6.3 亿参数）的 Heatmap 回归任务对显存挑战极大（前向激活值是真正的显存杀手）。
- **显存消耗预估：** 若采用 512×512 切片进行全参数微调（无任何优化），单卡显存预估需 60GB - 80GB 以上。
- **实战降显存组合拳：**
  - **PEFT 微调 (如 LoRA)：** 彻底冻结底层，仅在深层 Attention 模块旁挂载低秩矩阵进行权重微调，将优化器状态显存消耗直降 90% 以上。
  - **梯度检查点 (Gradient Checkpointing)：** 丢弃大部分中间激活值并在反向传播时重算，用 20~30% 计算时间换取海量显存空间。
  - **FlashAttention 机制：** 硬件层面的算法优化，极大缓解超长序列带来的平方级显存爆炸。结合 **BF16 混合精度** 能够兼顾动态数值范围不变（防治下溢），再省一半显存资源。

## 9. 国产异构算力卡迁移指南
若需迁移至国产异构加速卡（华为昇腾 Ascend、寒武纪 MLU 等）训练，需重点解决以下适配：
- **设备抽象化 (Device Agnostic Code)：** 全局替换底层硬编码的 `.cuda()` 为动态获取的方式（例如封装在 `device_utils.py` 获取 `torch.device("npu")` 等）。
- **特殊算子与 FlashAttention：** 标准的 `flash-attn` 是基于 CUDA 编写的无法直接运行，必须调用国产算子库中提供的对应融合 Attention 模块（如昇腾的 `npu_fusion_attention`）。目标检测相关的特殊操作须确认官方库底层C++的实现，防止严重掉速的“算子回退 (Fallback CPU)”。
- **分布式后端替换 (DDP Backend)：** 分布式训练中将 NVIDIA 的通信库 `nccl` 变更为特有通信库（华为对应 `hccl`，寒武纪对应 `cncl`）。
- **混合精度的兼容：** 将 `torch.cuda.amp` 调整为对应的硬件专用库函数（如 `torch.npu.amp`）。建议迁移初期先使用 FP32 跑通 Baseline 并在测试集上比对损失曲线与 mAP 水平一致后，再逐步开启混合精度。
